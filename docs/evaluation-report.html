Conclusion. The original skill reproduced the brand numbers correctly every time; what varied was judgment the skill left open: what to ask, how to handle text that overruns, which page type fits which content, how long a placeholder deck is, and whether to look at the result. Each source of drift was removed by turning the open judgment into a rule in SKILL.md or a method in the kit, then rerunning the same prompts three times. Across all nine cases the latest skill version passes every assertion in every run and no assertion flips. The remaining variation is wording the skill must invent (titles when the brief gives none, units in placeholder tables), which every run states in its reply. The suite is now saturated, so it needs harder cases to keep discriminating.

2. The problem

The same prompt produced visibly different outputs from run to run. The goal of the test plan (TEST-PLAN.md) was to measure how consistently the skill turns the same prompt into the same quality of output, find what varies, and verify that question gating removes "assumed and built the wrong thing" failures.

The baseline (iteration 1, the original skill) settled where the drift was. Every brand-mechanics assertion (Open Sans everywhere, palette-only colours, no shadows, gradients or rounded corners, footer and logo on content pages, 960 × 540 pt slides) passed in every run. The assertions that flipped were all about content handling and intake. In the words of the analyst notes for the complete-brief case, the brand assertions "do not discriminate".

Why output varied: six sources identified in TEST-PLAN.md

#SourceEffect
1No intake step.Format, page types, deck name, date, photos, spelling, slide count and the content itself were left to the model to guess.
2Photos required but never gated.With no image paths, runs skipped photos, drew placeholder rectangles, downloaded stock images or crashed the kit.
3Toolchain assumed, not checked.python-pptx, pdffonts and static Open Sans were all absent on the test machine, so each run improvised (installed, substituted or skipped verification).
4The 230-line kit lived inline.Every run had to transcribe it into newmont_kit.py, inviting transcription errors and partial rewrites.
5No content-to-page-type mapping.The same brief became a different slide structure each run.
6Verification unreachable."Render and look at every page" had no concrete command, so some runs rendered and fixed, others shipped blind.

3. The evaluation pipeline

Each case is run three times per skill version by independent Opus subagents that see only the skill and the prompt. Outputs are graded the same way every time by scripts, then by an LLM grader for judgment calls, and aggregated into a benchmark. The analyst reads the three runs side by side and writes variance.md; anything that varies becomes a patch to the skill or kit, followed by a rerun.

Run data path pattern: newmont-skill-workspace/iteration-N/<case>/<config>/run-K/ with outputs/, transcript.md, programmatic.json, grading.json, timing.json. Configurations: old_skill (the snapshot in skill-snapshot/, or in iteration 4 the pre-patch revised skill) and with_skill.

7. How determinism was engineered

Every flip traced back to a judgment the skill left open, never to a brand number. The working rule was: when a case flips, look for the missing rule or kit method rather than tightening wording.

PrincipleWhat it meansImplemented in SKILL.md
Move judgment into rules and kit methodsWhere runs chose differently, give one answer: a page type per content shape, one kit method per page type, placeholders built into the kit."Choosing page types"; "Making a deck (PowerPoint)" kit table
Must-have vs decide-and-state inputsOnly inputs that would make the output wrong if guessed are asked (content, format, photos, deck name and date). Everything else gets a default named in the reply."Before you build"; step 1 of "How to use this skill"
Fixed default outlinesA topic-only request always becomes the same 8 pages in the same order; a financial request the same two pages."Choosing page types" (default outline); "Financial results pages"
Hard thresholds ("exactly three")Three-column pages take exactly three points; four or more is a lead-in list; up to 8 items per page, a 9th starts a new page."Choosing page types" table
Keep words and geometry on overrunNever shrink type, widen boxes or move neighbours; name the line to cut. Restyles keep every sentence word for word."Choosing page types" (overrun rule); "Restyling an existing deck"
Executable checker plus render-and-lookcheck_deck.py checks fonts, palette, effects, furniture and size; LibreOffice render and a list of what to look for that a script cannot see."Checking before delivering"; setup check in "Making a deck"; step 4 of "How to use"
A reply format that states assumptionsOpen with assumptions and placeholders, then pages built, what was checked, departures one line each. What the skill must invent becomes visible and changeable."Checking before delivering" (Reply format); step 5 of "How to use"

The process the skill now prescribes (from "How to use this skill")

  1. Get the inputs. Compare the request with "Before you build"; ask once for any missing must-have, or build at once if nothing is missing.
  2. Map content to page types with the table and write the page list before coding.
  3. Run the setup check, then build with scripts/newmont_kit.py (never retyped).
  4. Check and look: run check_deck.py, render, open the pages, fix every FAIL.
  5. Deliver with the fixed reply format.

8. Caveats and limits

  • Open Sans is not installed on the test machine, so every LibreOffice preview used a substitute (serif) font. Line breaks in the previews may differ from PowerPoint with Open Sans. Runs were told to say so and not to switch fonts; all new-skill deck runs did.
  • python-pptx is not installed system-wide, so each run installed it its own way (scratchpad venv, pip --user). The harness itself uses a uv venv in the workspace.
  • Stored transcripts are summaries of final messages, not full tool logs. Assertions such as "checker run and deck rendered" are graded from the reply plus the renders/ folder.
  • Three runs per prompt is a small sample. 0 flips in 3 runs does not prove a flip rate of zero; a rare failure could still appear.
  • LLM graders (Opus) judge the judgment assertions. They are not deterministic themselves; programmatic checks cover what a script can measure.
  • Assertions are saturated at 100%. The latest version passes everything, so the suite no longer discriminates; it needs harder cases to keep finding drift. The long-content slide-count check was widened from 6 to 9 slides to 5 to 9 after the lead-in-list patch, so the correct 5-slide deck now passes it.
  • Suggested page types are not measured from the source deck: lead_in_list, kpi_tiles, fin_table and the financial pages are derived from its components and marked "suggested".
  • Round-three pins are untested: the Δ basis, table y, summary body size and footnote size were added after iteration 5 and not rerun. Off-palette and photo-backdrop were not rerun after the round-two patch.

9. How to rerun

Option A: claude plugin eval (from the skill folder)

cd /Users/bpatel/dev/newmont-skill
claude plugin eval . --allow-tools Write,Edit,Bash --scaffold

This runs the same case folders under evals/ (prompt.md front matter sets max_turns: 40, timeout_seconds: 900 and the allowed tools; place-files.sh scaffolds input files).

Option B: the workspace pattern used for this report

  1. Create newmont-skill-workspace/iteration-N/ and copy each case's eval_metadata.json (prompt and assertions) from the previous iteration.
  2. Launch 3 unattended Opus runs per case per configuration, each seeing only the skill and the prompt, with the brief rule: if you need something from the user, write questions.md and stop. Outputs go to <case>/<config>/run-K/outputs/.
  3. Run the programmatic graders: 
    /Users/bpatel/dev/newmont-skill-workspace/.venv/bin/python tools/grade_all.py iteration-N
  4. Spawn LLM graders (Opus, skill-creator agents/grader.md) for the judgment assertions; each writes grading.json into its run folder.
  5. Aggregate: 
    python <skill-creator>/scripts/aggregate_benchmark.py iteration-N --skill-name newmont-brand
  6. Build the review page and read the runs side by side: 
    python <skill-creator>/eval-viewer/generate_review.py iteration-N --skill-name newmont-brand \
  --benchmark iteration-N/benchmark.json --static review-iteration-N.html
  7. Write variance.md per case (passed in all, flipped, structural differences), patch the skill or kit, and repeat.
